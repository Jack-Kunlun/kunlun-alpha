# 节假日采集边界修复计划

## 范围

P1-N07 的有界缺陷修复，不是完整交易日历持久化实现。基线为 `6b62e93`。
当前 `CalendarProvider.fetch_holidays()` 返回闭市记录，而不是完整逐日交易日历；
无法由闭市记录的间隔或空列表推断交易日缺失。

本次只修复错误缺失告警和无界分页。持久化日历快照、修正层、时点查询、多源对账与
证券生命周期仍需独立设计和验证，不在本次变更中落地。

## 验收条件

1. 稀疏闭市记录和成功的空响应均不生成 `MISSING_DATE`；保留内部 legacy literal，
   不改变已有临时闭市和显式来源冲突告警的行为。
2. 采集结果明确 `coverage_status = UNKNOWN`。没有告警不表示日历完整。
3. 重复游标、自循环、多游标环路以及持续产生新游标的无界分页，均在有限请求内失败。
4. 页数上限为构造时的正整数参数，默认 100，拒绝布尔值和非正整数；最后一页恰好在
   上限内且无后续游标时允许成功，不额外请求第 101 页。
5. 分页或 provider 失败发生在保存前，不保存半份新快照，不改已有版本和审计记录。
6. 正常多页合并只保存一次，不丢失记录。分页保护的错误消息不包含游标或原始 provider 内容。

## 顺序与验证

先新增回归测试并运行观察失败，再最小修改 collector；运行日历相关测试、变更文件的
Ruff 格式/lint、Basedpyright 和必要的包构建。最后只读复核并记录新鲜命令输出。
原测试将长假期间隔解释为缺失，其期望需按 provider 契约纠正，而非保留伪语义。

风险为中等：变更采集流程与告警分类，但不引入数据库、迁移、凭据、权限或新依赖。
不修改原有 P6 文件，不提交本轮新增修复，不部署，不读取真实数据或运行自动门禁。

## 仍未满足的前置条件

现有 repository 仍为内存实现；source/year/exchange 复合身份、持久化版本、来源证据、
修正审计的可见时间和 PIT 读取尚未形成完整链路。未来日历必须区分“规则适用日期”和
“来源信息已知时间”，不能因节假日尚未来临就隐藏已经发布的安排。
本次也不新增 provider 返回交易所/年份的一致性校验或多源比较调用；这些仍需后续修复。
